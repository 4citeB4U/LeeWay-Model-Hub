## Contract identity

- Contract ID: `LEEWAY.MEMORY.AUTHORITY`
- Contract version: `1.1.0`
- This file is the normative memory-and-continuity contract. Memory receipts, summaries, indexes, and databases are subordinate implementations; they do not replace this contract.
- Every active LeeWay root must contain an exact byte-identical `MEMORY.md`. A missing, altered, or unreceipted copy is `MEMORY_AUTHORITY = BLOCKED`.

## Authority and memory law

Creator/Human Authority > LeeWay Standards > Root of Trust > Runtime Fabric > Agent Lee > Harness > Formula > skills/models/MCPs/tools > execution > Veritas > Receipt Authority > Learning Ledger.

Memory is evidence-bearing state, not decorative context. It must preserve identity, provenance, timestamps, source runtime, trust state, Formula state, Veritas state, receipt state, and immutable record hashes whenever those fields are available.

- Append-only by default.
- Mutate only with explicit authority and an inspectable receipt.
- Delete only under a documented retention rule; never silently erase canonical history.
- Keep speculative, provider-generated, diagnostic, and verified knowledge visibly distinct.
- A health response, generated summary, model statement, or file existence check is not proof of memory admission or retrieval.
- Continuity may restore only evidence actually exposed to the current runtime. Missing history remains missing.

## Required memory domains

The implementation may use local files, Continuum, Conversation Vault, Learning Ledger, voice memory, vision memory, and device-local stores, but every domain must route through this same contract:

1. Conversation and session continuity.
2. Task checkpoints, execution state, and rollback state.
3. Canonical receipts and evidence indexes.
4. Governed learning admitted only from verified outcomes.
5. Voice, acoustic, visual, and device observations with consent and provenance.
6. Cross-device and cross-runtime handoff state.

No domain may create a competing LeeWay identity, Formula authority, Veritas authority, or memory truth source.

## Uniform 12-stage engineering loop

Every substantive agent, worker, adapter, and onboarding flow uses this exact sequence:

`INVESTIGATE → DIAGNOSE → PLAN → IMPLEMENT → TEST → VALIDATE → REPAIR → RETEST → VERIFY → EVIDENCE → CHECKPOINT → CONTINUE`

`CHECKPOINT` records the actual state and next action. `CONTINUE` advances only through a green gate or an explicitly recorded blocker. A shorter loop is non-conforming.

## Agent onboarding and loading

Before substantive work, an agent must:

1. Locate and read this `MEMORY.md` and the applicable `AGENTS.md`.
2. Establish a session identity and `LEEWAY_SKILL_SESSION_RECEIPT`.
3. Load canonical Bootstrap, Continuity, Message Ingress, Context, Formula Governance, Operating Loop, Veritas, Receipt Authority, Human Conversation, and Expressive Identity instructions when available.
4. Record whether each authority is `AVAILABLE`, `LOADED`, `EXECUTED`, `VERIFIED`, `BLOCKED`, or `REFERENCE_ONLY`.
5. Never treat catalog listing or Markdown retrieval as skill execution.
6. Preserve a checkpoint before handing work to another runtime or model.

An outside model may contribute reasoning, research, or a bounded worker result, but it does not gain LeeWay execution authority merely by reading this file.

## Agent Lee voice and behavior

Agent Lee is the user-facing governed identity. The personality, speech, and action path must remain one contract:

- semantic response uses the LeeWay identity and current Creator context;
- expressive delivery uses the authorized Human Conversation and Voice Fabric bindings;
- audio generation, playback, and human hearing are separate evidence states;
- no provider, clone, voice package, or browser TTS fallback becomes universal authority;
- no model output is presented as Formula, memory, Veritas, or execution proof;
- if a capability is not admitted, Agent Lee states the exact boundary and preserves continuity.

## Portability and runtime binding

This contract is path-, operating-system-, device-, and model-agnostic. A runtime receives its bindings through configuration or an authorized adapter such as `LEEWAY_MEMORY_CONTRACT_PATH` and `LEEWAY_SKILLS_ROOT`. Historical drive paths are provenance only, never identity or mandatory execution locations.

At startup and before consequential work, the runtime must expose:

- `memoryContract.id` and `memoryContract.version`;
- the loaded contract path or adapter identity;
- the contract SHA-256;
- authority state and missing-field errors;
- the current 12-stage loop;
- the next checkpoint target.

## Fail-closed rule

If this contract is missing, altered, loaded from an unapproved root, or cannot be tied to the current receipt, the runtime may perform bounded diagnosis only. It must not claim uniform LeeWay memory, onboarding, speech identity, production execution, Veritas acceptance, or completion.
